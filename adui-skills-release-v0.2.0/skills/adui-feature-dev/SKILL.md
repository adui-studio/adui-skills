# ADui 功能开发

按“理解 → 计划 → 最小实现 → 验证 → Review → 交付”的顺序完成开发任务。不要因为能立即写代码就跳过上下文理解和验证。

## 工作流程

1. 判断任务类型：新功能、Bug 修复、重构、配置修改、性能优化或测试补充。
2. 先读取现有项目约束、相关文件和调用链；技术栈不明确时优先配合 `adui-stack-router`。
3. 用简短内容复述目标、输入输出、关键约束和验收标准。
4. 只对会影响正确性的缺失信息提出问题；非关键细节采用明确、可回退的假设。
5. 识别风险：兼容性、公共接口、状态与并发、权限与输入、安全、数据迁移、资源释放、构建与版本差异。
6. 制定最小改动方案；不要无故调整目录、公共 API、依赖、命名风格或无关业务逻辑。
7. 实现修改，并保持与项目已有代码风格、框架约定和依赖版本一致。
8. 对核心逻辑补充或更新测试；Bug 修复优先增加能够复现问题的验证。
9. 执行适用于当前项目的质量门禁：格式化、Lint、类型检查、单测、集成测试、构建和必要的运行验证。
10. 检查 Git diff，确认没有无关改动、敏感信息、调试残留和破坏性操作。
11. 按 `references/output-contract.md` 交付结果，并明确仍未确认的问题。

详细流程见 `references/workflow.md`；质量门禁见 `references/quality-gates.md`。

## 开发原则

- 以理解需求为前提，不盲目开写。
- 以正确可靠为目标，不虚构 API、版本、运行结果或测试结果。
- 以最小改动为默认策略，不为“更漂亮”而扩大改动范围。
- 解释关键原因，不只给代码。
- 主动检查安全边界，不把密钥、密码或 Token 写入代码。
- 重要结论必须有实际验证证据；没有执行过的命令必须明确说未执行。
- 优先简单、清晰、可维护的实现，避免无必要抽象和炫技。
- 对现有项目优先遵守仓库内 `AGENTS.md`、README、Lint/Format 配置和既有模式。

## 与其他 Skills 协作

- 技术栈或 Profile 不明确：先用 `adui-stack-router`。
- 复杂 Debug：使用 `systematic-debugging`。
- 适合测试先行的核心逻辑：使用 `test-driven-development`。
- Web UI：按项目 Profile 使用 Vue/React、Tailwind/UnoCSS 和 UI/Accessibility Skills。
- 数据库：按真实 provider 使用 Prisma、PostgreSQL、MySQL 或 SQLite Skills。
- 3D/GPU：先遵循 `adui-3d-architecture` 的引擎选择，再使用具体引擎 Skill。
- Git 提交、PR、Release：使用 Git Profile；除非用户明确要求，否则不要自动 commit、push、merge 或 release。

## 安全边界

- 不读取或输出与任务无关的 `.env`、私钥、Token、凭据和 Secret。
- 不执行 `git reset --hard`、强制推送、大范围删除、数据库破坏性迁移等高风险操作，除非用户明确要求且风险已说明。
- 不为通过测试而弱化权限、关闭安全校验、删除有效测试或吞掉异常。
- 数据库 schema 或迁移变更必须说明兼容性与回滚风险。
- 涉及用户输入、文件路径、SQL、命令执行、权限、网络请求时主动检查注入与越权风险。
