# ADui 功能开发工作流

## 1. 进入任务

先确认任务属于哪一种：

- 新功能：重点确认输入、输出、交互、状态与验收标准。
- Bug 修复：先复现或建立可靠证据，再定位根因。
- 重构：必须保持外部行为不变，并明确重构边界。
- 性能优化：先有基线或明确瓶颈，不凭感觉优化。
- 配置/依赖修改：先核对当前版本和项目约束。

## 2. 建立上下文

按最短路径读取：

1. 仓库级 `AGENTS.md`、README 和项目配置。
2. 用户点名的文件或模块。
3. 调用方、被调用方、类型、测试和配置。
4. 技术栈不明确时运行 `adui-stack-router`。

不要为了“全面了解”而无边界扫描整个仓库。

## 3. 需求复述

编码前至少确认：

- 目标是什么。
- 输入和输出是什么。
- 哪些行为不能改变。
- 边界/异常如何处理。
- 什么结果算完成。

信息不足但不阻塞正确性时，明确假设后继续；会影响公共接口、数据结构、权限或业务结果时再询问。

## 4. 计划最小改动

优先级：

1. 修正已有实现。
2. 复用已有公共能力。
3. 新增局部能力。
4. 只有确有必要才重构公共层或引入依赖。

计划中列出修改文件、原因、风险和验证方式。

## 5. 实现

- 遵守现有目录与代码风格。
- 不顺手修无关问题；发现无关问题可在交付时单独说明。
- 公共接口变化必须说明影响范围。
- 新增依赖前检查是否已有等价依赖，并说明引入理由。
- 不硬编码 Secret、环境地址和账号信息。

## 6. 测试与验证

根据项目实际能力选择：

```text
格式化
  ↓
Lint
  ↓
类型检查 / 静态分析
  ↓
单元测试
  ↓
集成 / E2E
  ↓
Build
  ↓
必要的运行验证
```

不是每个项目都必须有全部步骤，但跳过的关键步骤要说明原因。

## 7. Review

交付前检查：

- Git diff 是否只有必要修改。
- 是否有调试输出、临时文件、TODO 占位。
- 是否有安全风险或敏感信息。
- 是否改变公共行为但未说明。
- 测试是否覆盖正常、异常和关键边界。
- 文档是否需要同步更新。

## 8. Git 交付

默认只给出建议，不自动执行写操作：

- 推荐 commit type/scope。
- 给出建议 commit message。
- 需要 PR 时总结变更、验证和风险。
- 用户明确要求后再执行 commit、push、PR 或 release。
